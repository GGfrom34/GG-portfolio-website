Building This Site

Problem

I needed a portfolio that argues for itself: something a senior PM actually built by directing Claude Code and AI agents, not a templated site-builder export. That ruled out frameworks and page builders in favour of plain HTML/CSS/JS, one repo, and one deploy target — GitHub Pages — reviewable one change at a time like real software, rather than a single wall of generated markup nobody ever looks at again.

The catch was I started from an empty folder with no Git installed, no GitHub CLI, and no existing repo conventions to follow. Every later request — a link change, a rename, a favicon, a whole new case study — needed to land through the same disciplined path: a branch, a real commit message, a pull request, a merge, and a clean-up, not a shortcut taken because it was "only two lines."

Approach

I started by asking for the scaffold itself: a home page with a one-line pitch, two case-study placeholders, a shared stylesheet, and header/footer link placeholders for CV and LinkedIn — kept deliberately plain over elaborate. From there I drove every change as its own small, reviewed unit: rename this case study, change these two links, add a favicon, backfill this content — each one previewed in an actual browser at desktop and mobile widths before I ever saw it, then pushed through a branch → PR → merge cycle rather than committed straight to main.

The environment fought back more than the content did. Git wasn't installed, so I got a walkthrough for the winget install and a PATH fix, then had to work around a shell process that couldn't see the newly installed git.exe until every command re-pointed at its full path. The GitHub CLI had the same problem — install it, hit the missing PATH again, and only after gh auth login could pull requests open automatically. Even then, a multi-line PR body broke on PowerShell's argument quoting, which needed a switch to --body-file to fix cleanly.

Approach — step by step

  • I set the workflow standard, and Claude Code held it for the rest of the session. Once I approved the first branch → PR → merge cycle for a small link change, Claude Code kept using it for every subsequent change without being asked again, including checking with me before every push and every merge.
  • I made every account and tooling call myself. Installing Git and the GitHub CLI, running gh auth login in my own terminal, and approving each push and merge were mine to do; Claude Code diagnosed the underlying PATH and quoting problems and told me exactly what to run.
  • I chose between the options it generated, rather than getting one default. Claude Code designed five distinct "GG" favicon concepts — a circle badge, a hex circuit, a duotone tile, a circuit chip, and a minimal wordmark — and rendered them together for a side-by-side comparison. I picked the hex-circuit option, and only that one was wired into the site.
  • I asked for verification, not just claims. Every visual change was checked by starting a local preview server and taking real screenshots at desktop and mobile widths, not accepted as "should work" from reading the code alone.
  • I kept unrelated work out of my commits. When another session's work (the Tariff Advisor backend) landed in the same working directory, Claude Code staged and committed only the files relevant to the task at hand rather than sweeping everything in with a blanket git add -A.

Claude Code capabilities used

  • File scaffolding and iterative editing — generated the initial HTML/CSS/JS structure, then made every follow-up change as small targeted edits rather than regenerating whole files.
  • The in-app browser — previewed every visual change against a real local server, at desktop and mobile widths, before calling it done, and screenshotted the result to confirm the favicon actually showed in the browser tab.
  • Generated visual concepts — designed and rendered five distinct favicon options inline for a side-by-side comparison, rather than describing them in words.
  • Git and GitHub CLI operations — initialised the repo, and ran every branch, commit, push, pull request, and merge for the session once the workflow was approved.
  • Diagnosing environment issues rather than guessing — traced a missing git/gh command to a stale shell process rather than a bad install, and a broken pull-request body to PowerShell's argument quoting rather than the GitHub CLI itself.

Outcome

  • A live, plain HTML/CSS/JS portfolio at ggfrom34.github.io/GG-portfolio-website, deployed via GitHub Pages with no build step and no framework.
  • Every change since the initial scaffold — link edits, a case-study rename, a favicon, this very case study — shipped through its own reviewed pull request, merged deliberately rather than committed straight to main.
  • A consistent visual identity: a "GG" hex-circuit favicon reused as a centred logo on every page, matching the site's existing accent colour.
  • A working template for future changes — branch, preview in a real browser, PR, merge, clean up — proven across half a dozen real changes, not just described.
