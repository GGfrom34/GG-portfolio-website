Octopus Tariff Advisor

Problem

Octopus Energy sells seven-odd household electricity tariffs (Flexible, Agile, Go, Cosy, Intelligent Octopus Go, Outgoing, Agile Outgoing), and which one is actually cheapest depends on a combination of things a generic comparison table can't capture: whether you have solar panels, whether your EV charges overnight or whenever you happen to plug in, whether a home battery can arbitrage price swings. Getting this right means reasoning about the mechanics — not just looking up a flat rate.

I wanted a tool that answers immediately from whatever a visitor happens to say first, states plainly which assumptions the answer rests on, and only then asks for the specific details that would sharpen it — rather than a form to fill in before it will say anything at all. And I wanted that agent reachable by anyone visiting this site, not locked inside my own Claude Code session.

Approach

The project is built in layers, each added as its own piece of work. A dependency-free Python engine (core.py) simulates a representative day of energy flows against each tariff's actual half-hourly prices — not a single fixed usage profile re-priced per tariff, but a fresh simulation per candidate, since a battery or a smart EV charger behaves differently on a flat rate than it does on Agile. That engine has no knowledge of any interface: a CLI and an MCP server (for Claude Desktop/Code) were built as thin adapters on top of it, sharing a single "answer first, then offer to refine" behavioural contract so the assumptions a result rests on are always structured data, not something an LLM has to remember to mention.

The most recent layer — and the one embedded live below — is a public web chat backend with its own persona, reusing that same engine and behavioural contract rather than duplicating any tariff logic. Since it's a public, unauthenticated endpoint spending real API credits, most of the work went into guardrails: a persisted daily token budget (global and per visitor), rate limiting, and tight per-call caps, deployed to Render and load-tested against real conversations rather than just written and assumed correct.

Claude Code capabilities used

  • I set the architecture direction before any code was written. I asked for real build options — direct API integration vs. a remote MCP connector vs. a subprocess bridge — weighed the trade-offs myself, and picked the approach. Claude Code then used Plan Mode to scope that specific approach in detail before touching a file.
  • I pushed the guardrails further than the first draft. The first plan only capped spend per visitor, with no ceiling on total spend across everyone combined. I asked for that to be tightened and set the actual number myself — a hard 10,000-token daily cap across every visitor — rather than accepting the looser per-visitor-only version.
  • I made every account, credential and hosting call myself. I created the Render and Anthropic accounts, generated and scoped the API key, set the spend limits, and chose the hosting tier. Claude Code was explicit about which of those steps were mine to do, and built the deployable code and config around the decisions I made.
  • I found the bugs by using my own product, then directed how they got diagnosed. I tested the live chat myself, caught two real problems — a follow-up question failing, the "answer first, then refine" flow never appearing — and specifically asked for a root-cause diagnosis rather than a guess. That's what led to fixing an actual Anthropic SDK gotcha and a token-truncation bug, both now locked in with regression tests.
  • I called the trade-offs, every time one came up. Free Render tier and its caveats vs. a paid plan, a lightweight keep-alive ping vs. a database migration, a plain reminder vs. full API automation for a scheduled change, one combined commit vs. splitting a tangled working tree in two — each was a decision I made after being given the actual options, not a default Claude Code picked on its own.

Outcome

  • A working, publicly hosted chat agent, embedded live on this page below — the same recommendation engine now sits behind three independent interfaces (CLI, MCP, web chat) without a single line of tariff logic duplicated between them.
  • Guardrails that were actually tested against their own edge cases, not just written and assumed correct: a persisted per-visitor and global daily token budget, a rate limit, and a keep-alive workflow that closes a real bypass discovered during testing.
  • Two genuine bugs found and fixed through live testing rather than in a vacuum — a token-truncation issue that silently broke the "answer first, then refine" flow, and a follow-up-message failure traced to a specific SDK serialisation detail — both locked in with regression tests, not just patched and forgotten.
